# 第六批整改：版本化比较规则 + 数据库备份/恢复（F08 尾巴收口）

日期：2026-10-19。源码服务版本：**2026.10.19.4**（前端构建参数 `20261019-rules-backup`，`polish.css?v=20261019a`，`app.js`/`software-settings.js?v=20261019e`）。

**本批收口 F08 尾巴：版本化比较配置 + 物理备份/恢复界面。F07 遗留旧导出接口并入统一报告中心、F09 站码碰撞修复均已在上一轮完成，本批不重复。**

## 背景与缺口

第四/五批复盘时明确列出 F08 尾巴两项未做：

1. **版本化比较规则**：`analysis_reporting.py` 的缺陷匹配容差（`match_tolerance_mm`）此前写死为 0.01，无法按版本切换、无法审计"用哪套规则得出的结论"，对比/快照缺乏可追溯的口径快照。
2. **数据库的备份与恢复**：台账是全量 72 次大修 4867 条真实 ECT 明细的单一 SQLite，此前没有"立即备份 / 导出到指定目录 / 从备份恢复"的可操作入口，一旦误删/误改缺少兜底。

本批把这两块补齐，并配套桌面端设置面板与 Electron 文件夹/文件选择对话框。

## 本批实施

### 后端（`src/backend/server.py`，冻结接口语义、未新增任何第三方运行时依赖）

1. `init_db` 新增两张表：
   - `analysis_rules`：`version UNIQUE`、`name`、`match_tolerance_mm`、`note`、`created_by`、`created_at`、`is_active`。种子一条 `version=1`「初始匹配规则」、`match_tolerance_mm=0.01`（注意种子版本号是 1，不是 0；`DEFAULT_RULES` 仍保留 `version=0` 作为代码回退常量）。
   - `restore_points`：记录每次备份（`path`、`kind`、`note`、`record_count`、`created_at`），供列表展示与"恢复前自动安全备份"追踪。
2. 规则接口：
   - `active_analysis_rules()`：取 `is_active=1` 中 `version` 最大的一条；无记录则回退 `DEFAULT_RULES`。
   - `list_analysis_rules()`：全部规则按 `version DESC` 返回。
   - `create_analysis_rule(name, match_tolerance_mm, note)`：校验名称非空、`0 < 容差 ≤ 5`、版本号自动递增（取当前最大 +1）、把旧版本 `is_active=0`、新版本激活，返回新规则。
3. 备份接口（均走 SQLite 在线备份 `source.backup(target)`，WAL 模式安全）：
   - `create_database_backup(note="", target="", kind="")`：文件名带 `uuid.uuid4().hex[:8]` 防撞；`kind` 显式传入（如 `safety`）或按 `target` 是否为默认目录推断（`manual`/`exported`）。
   - `list_database_backups()`：返回 `restore_points` 列表。
   - `validate_backup_file(path)`：拒绝"当前库自身"（路径相同）、拒绝缺失文件，并报告该备份所含 `findings` 记录数。
   - `restore_database(path)`：见下方"恢复实现"。
   - `_sqlite_backup_to(src, dst)`：封装 `src.backup(dst)`，统一连接管理。
4. 路由注册（GET/POST）：
   - `GET /api/analysis-rules` → `active_analysis_rules()` + `list_analysis_rules()` 合并返回；
   - `POST /api/analysis-rules` → `create_analysis_rule`（body：`name`/`match_tolerance_mm`/`note`）；
   - `GET /api/backups` → `list_database_backups()`；
   - `POST /api/backup` → `create_database_backup`（body：`note`/`target`/`kind`）；
   - `POST /api/backup-validate` → `validate_backup_file`（body：`path`）；
   - `POST /api/restore` → `restore_database`（body：`path`）。

## 两个真实生产级 bug（由本轮测试捕获并修复）

写 `tests/test_backup.py` 的"恢复后找回删除记录"用例时，暴露了会在真实桌面运行场景触发的两个 bug：

1. **备份文件秒级时间戳撞名覆盖（数据静默丢失）**：`create_database_backup` 原用秒级时间戳命名。恢复流程会先做一次"安全备份"，若安全备份与待恢复备份落在同一秒，安全备份会**覆盖**待恢复备份——结果恢复后 `findings_after=0`（本该 ≥1），等于把用户想恢复的数据覆盖没了。
   - 修复：文件名追加 `uuid.uuid4().hex[:8]` 防撞；安全备份使用独立前缀 `backup_safety_`；`create_database_backup` 增加显式 `kind` 参数，恢复时传 `kind="safety"` 与导出/手动备份区分开。
2. **WAL 恢复残留锁（恢复失真 + 文件锁死）**：初版恢复用 `src.backup(db)` + `wal_checkpoint(TRUNCATE)`。WAL 模式下残留的 `db.db` 连接锁导致 `restore_points` 的插入未真正提交（note 全空），且测试 teardown 触发 `PermissionError: WinError 32`（文件被占用无法删除）。真实环境同样会锁死库文件、恢复结果不可信。
   - 修复：改用**整库换名覆盖**——`validate_backup_file` → 安全备份（`kind="safety"`）→ 把备份在线备到临时库 `db.db.restoring` → 关闭连接后删除旧 `db.db`/`-wal`/`-shm` → `stage.replace(db_path)` → 重新打开读 `findings_after` → 写 `operation_logs`。彻底规避 WAL 残留锁。复刻脚本验证锁已消除、`findings_after=1`。

这两个 bug 在未写测试时不会被发现；在真实桌面"恢复最近一次删除"的高频场景下必然触发，属本轮高价值产出。

## 使用与限制

入口：桌面端"软件设置"页新增两块——

- **对比规则版本**：查看当前生效规则与历史版本，新建规则（填名称、匹配容差毫米、备注）即激活并自动停用旧版本；后续分析/快照按激活规则出指纹。
- **数据库备份与恢复**：一键备份到默认目录、或选目录导出；列表可查看每次备份的类型/路径/记录数；恢复需从文件选择框选定备份、二次确认（红框风险强调）后整库换名覆盖，恢复前自动做一次安全备份，落 `backup_safety_` 前缀。
